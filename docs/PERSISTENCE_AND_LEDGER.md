# Persistence and ledger contract

`db/001_partner_platform.sql` is the durable PostgreSQL contract for the partner platform. `npm run db:migrate` now applies numbered SQL files transactionally and records them in `schema_migrations`; it requires an explicit `DATABASE_URL` and never falls back to the in-memory demo.

The schema stores money in integer minor units, separates subscription/payment/qualification/commission records, and models payout requests independently from provider attempts. `ledger_transactions`, `ledger_lines`, `partner_rank_snapshots` and `rank_events` are append-only: update/delete triggers reject mutation, while a deferred constraint trigger requires every ledger transaction to have one currency and equal debit/credit totals. `QualifiedPaymentRepository.process` is the durable post-verification payment boundary that commits qualification, L1/L2 commission snapshots, direct-L1 rank increment, balanced ledger entries and outbox events atomically; it does not accept raw browser payment claims.

Wallet values are read from the `wallet_projections` view. A payout lock and settlement are compensating ledger moves; an API handler must never set a balance column directly. `idempotency_records` and provider-scoped `webhook_events` protect retry paths, while `audit_logs` and `financial_rule_versions` preserve the explanation and rule version for every administrative change.

Full verified refunds and chargebacks are persisted in immutable `payment_adjustments` records. Each commission receives a durable `commission_events` state transition and a balanced compensating ledger move: held/available funds move to `REVERSED`, while already-paid funds move to `DEBT`. A direct L1 is decremented only when no other non-adjusted qualified payment remains for that attribution; renewals therefore do not create or remove duplicate rank counts. Partial adjustments fail closed until a versioned allocation policy is implemented.

Migration `005_partner_engagement.sql` seeds the configured non-financial achievements and adds idempotent leaderboard snapshot keys. `PartnerEngagementRepository` synchronizes achievement unlocks and Ambassador eligibility from the persisted L1 count, emits outbox events once per unlock/change, and computes public Top-100 snapshots from qualified metrics; private profiles are excluded and regional ranking fails closed until a real partner-region field exists.

The domain `TransactionalOutbox` mirrors `event_outbox`: producers enqueue payment, payout, refund, rank, and notification events transactionally, workers retry un-published events, and a published event is immutable. `PostgresPartnerRepository.recordRankEvaluation` provides the corresponding locked, idempotent rank projection boundary: partner state, `rank_events` and `partner_rank_snapshots` commit together. `SubscriptionRepository` provides the durable trial/reminder/provider-event boundary with duplicate delivery handling. The payout lock/settlement repository and signed webhook gateway are implemented; provider dispatch and its worker/reconciliation deployment still need a real provider adapter before production enablement.

The web server performs a bounded `SELECT 1` probe when `DATABASE_URL` is present. A configured URL with an unreachable database reports `ERROR` in `/api/ready` and cannot be treated as a healthy dependency. `PostgresPartnerRepository` now provides a projection boundary for authenticated dashboard, wallet, privacy-safe L1/L2 network, ledger and payout-history views; the dashboard uses the latest persisted rank snapshot so a grace/frozen rate is not silently recomputed from current defaults. Partner read routes use it only after identity and database checks; write-side financial orchestration still remains disabled until its transactional implementation and provider guards are supplied.

Before enabling the migration in production, run it against an isolated staging database and add application-level transaction tests for concurrent payout locks, webhook retries, refund reversals and reconciliation mismatches.
